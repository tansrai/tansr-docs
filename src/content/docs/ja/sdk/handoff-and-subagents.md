`createSession` で複数ターンのセッションを開き、[チェックポイント](/ja/sdk/checkpoints/)で保存と再開ができるところまでは、すでに使えます。このページは、その次に起きる三つの場面です。目標が変わって新しいセッションが欲しいとき、会話が長すぎて進行中のターンが真っ二つにされそうなとき、そして仕事をサブエージェントへ渡すときです。渡すなら、順番にやるか、並べてやるか、途中で向きを変えられる常駐にするか、を選びます。

まず、手元のパッケージを確認してください。いま npm から入る `@tansr/sdk` 0.20.1 と CLI 0.11.0 には、以下の呼び出しは**まだありません**。それらを含む版へ上げるまでは、この節のとおりに書いたコードは動きません。生成される記号ページも、今インストールできるパッケージから作られるので、これらの名前はそこにもまだ出ません。

## 目標が変わったら、このセッションを渡す

今のセッションには結論も、変更したファイルも、コンパクション済みの要約もあります。でも次にやることは、元の目標ではありません。元のセッションを無理に曲げず、新しいセッションに履歴全部を読み直させないでください。`handoffSession` は今のセッションを読むだけです。新しい目標向けの要旨を書き、その要旨だけを持つ新しいセッションを開きます。元のメモリ、スナップショット、ディスク上の記録はそのままなので、あとから戻れます。

```ts
import { handoffSession } from '@tansr/sdk';

const next = await handoffSession(session, {
  goal: 'ship the retry change',
  reviewDraft: (draft) => ({ action: 'confirm', briefing: draft.briefing }),
});
if (next.status === 'created') {
  console.log(next.sessionId, next.parentSessionId);
}
```

渡すのは新しい目標 `goal` です。空白を除いたあと、空ではいけません。空ならモデルは呼ばれず、結果は `rejected`、理由は `invalid_goal` です。

任意の項目は次のとおりです。

- `instructions` は要旨への追加の注文です。`signal` がどの段で中止しても結果は `cancelled` で、中途半端な新しいセッションは残りません。
- `reviewDraft` は、作る前に要旨を読むためのものです。コールバックは元のセッション id、目標、要旨の本文、ファイル一覧を受け取ります。本文を書き換えて確認するか、`{ action: 'cancel' }` を返せます。書き換えた本文が空白なら `rejected`、理由は `empty_briefing` です。
- 指定しなければ、新しいセッション id は新しい UUID、題名は目標のテキスト（64 文字を超えると切る）、作業ディレクトリは今のセッションのままです。`meta` に入れた項目は新しいセッションへ書かれます。`parentSessionId` と `handoffGoal` は必ず書かれ、どのセッションから渡され、そのときの目標は何だったかが残ります。
- `client`、`model`、`store`、`maxSummaryTokens` は、モデルや保管先を替えるとき、または要旨の長さを限るときだけ渡します。このセッションがルートの `createSession` で作られておらず、使えるモデルも無いときは `rejected`、理由は `unsupported_session` です。

次の場合もモデルは呼ばれず、新しいセッションは作られません。すでに閉じている（`session_closed`）、または今のターンがまだ動いている（`turn_running`）。モデルを組み立てられないときは `model_resolution_failed` です。要旨が書けなかったときは `failed` で、`reason` と `message` を見てください。新しいセッションが作れなかったときは `failed`、理由は `session_create_failed` です。

成功すると `status` は `created` です。新旧のセッション id、目標、要旨、ファイル一覧、種メッセージが入ります。開いた `session` と、要旨に使った `usage` が付くこともあります。

同じ `createSession` から作ったセッションには、列挙されない `session.handoff(options)` もあり、同じことをします。型の上ではエクスポートされた `handoffSession` を呼んでください。一緒に出るものには、種メッセージの印 `HANDOFF_PROVENANCE_TAG`（値は `tansr-handoff-v1`）、そのメッセージを組み立てて読み戻す `buildHandoffSeedMessage` と `readHandoffProvenance` があります。

CLI の対話画面では `/handoff <goal>` が同じ道です。目標を書かないと、使い方は `/handoff <goal>` だと示すだけで、モデルは呼ばず、見ているセッションも変わりません。要旨が出たあと、Esc または Ctrl+C で取り消せます。確認すると画面は新しいセッションへ移ります。元のセッションはディスクに残るので、`/resume` で開けます。

## 以前の地点から別の道を開く

[チェックポイント](/ja/sdk/checkpoints/)の `session.fork(checkpointId)` は変わりません。スナップショットから新しいセッションを複製します。すでに確定した地点から分かれ、要約には分岐のあとで増えた分だけを載せるなら、`restoreWithBranchSummary` を使います。

- `checkpointId` だけなら、同じ線をまっすぐ戻す復元のままです。
- `allowSibling: true`、または別の履歴を `targetMessages` に直接入れると、同じ起点を持つ兄弟へ切り替えます。要約が覆うのは二本の履歴が分かれたあとの差分と、ファイル一覧だけです。分岐点より前の冷たい区間を、もう一度まるごと走査することはありません。
- 成功すると `status` は `installed` です。復元前の保護用スナップショット `preRestoreCheckpointId`、導入前後のメッセージ数、ときには分岐点 `lcaIndex` が返ります。要約は 1 本だけです。普段の `session.restore` の動きは変わりません。
- 引数が不正なら `rejected` / `invalid_options` です。ルート入口で作っていないセッションは `unsupported_session` です。材料がもう合わないときは `source_invalidated` です。取り消したときは `cancelled` です。

## ターンの途中なのに、コンテキストが溢れた

コンパクションがターンの途中で起きると、あとのモデルが見る要約は二つに分かれて書かれます。すでに終わった履歴と、このターンのまだ終わっていない接頭辞（あなたの依頼、済んだ動作、これから続ける現場）です。ツール呼び出しとその結果が、要約の両側へ割られることはありません。次のコンパクションは、まずこの包みをほどきます。同じ接頭辞を何層にも重ねません。

コンパクションをもっと早く始められますが、それは既定ではありません。コンテキストの閾値に `backgroundCompactMargin`（何トークン早くするか）を足します。使用量がその早い線に届いても、今出している依頼はそのまますぐ送られ、バックグラウンドはその時点の読み取り専用スナップショットだけを要約します。この早め幅は 0 より大きい有限の数でなければなりません。`0`、負数、数でない値は例外になります。この項目を書かなければ、今使っているパッケージと同じで、余分な水位は出ません。

次の関門は、まだ同じ版かどうかを見ます。セッションを空にした、巻き戻した、または同期のコンパクションがそのスナップショットをすでに越えているなら、バックグラウンドの要約は捨てられ、差し込まれません。セッションを閉じるとき、`closeAsync()` はその仕事の終わりを待ち、使用量を記録します。

コンパクション、分岐の要約、その場限りの題名や分類は、キャッシュの印を書きません。主の会話が、それらの補助を本文の一部として読み返すことはありません。あなた自身のセッション依頼と、常駐サブエージェント自身のターンは、これまでどおりのキャッシュのままです。

最初のターンで使ったツール定義は、キャッシュの接頭辞として固定されます。あとから有効にしたツールは、その接頭辞の後ろへ足すだけなので、接頭辞全体を書き直す必要はありません。

## ツールが多すぎるときは、全部を一度に渡さない

既定では検索ツールは増えません。組み立てのときに `deferredDiscovery` を渡したときだけ、遅延読み込みのツールが数に応じて `ToolSearch` にまとまります。

- 遅延候補が閾値に達したときだけ `ToolSearch` を登録します。閾値の既定は 16 で、`threshold` で変えられます。セッションの途中で MCP をさらに足すなら、`force: true` にすると 16 未満でも `ToolSearch` を先に置きます。
- 閾値未満で、強制でもないとき、直接渡したツールはこれまでどおり載ります。これが `eagerBelowThreshold` の既定（`true`）です。
- モデルが呼ぶとき、`query` は空ではいけません。必要な能力を一文で書くか、ツール名を正確に書くか、`select:tool_a,tool_b` で名前を指定して読み込みます。`limit` の既定は 5 で、1 から 20 までです。見つかったツールは、今すぐ直接呼べる集合へ足されます。
- この説明の文は固定です。途中で MCP をつないでも外しても、目録全体がシステムプロンプトへ貼られることはなく、この文も変わりません。
- サブエージェントは各自の目録を持ちます。ほかがたった今有効にしたツールは見えません。実際に実行するときは、これまで設定した権限の確認を通ります。

## 仕事をサブエージェントへ渡す

一つの仕事なら、これまでどおり単一の `Task` です。`prompt` と `description` の両方を書きます。`run_in_background: true` を受け付けるのはこの形だけで、バックグラウンドで走らせられます。

順番に数段やるなら `chain` で、1 から 6 段です。次の段は `{previous}` で前の出力を受け取ります。途中の本文は、このセッションの履歴へ書かれません。最後に見えるのは、鎖全体の結果です。

並べて数件やるなら `tasks` で、1 から 8 件です。`concurrency` の既定は同時に 4、範囲は 1 から 8 です。`policy` の既定は `allSettled` で、全部の結果を待ちます。`failFast` は一件でも失敗したら、まだ終わっていない兄弟を止め、資源が片付くまで待ちます。`concurrency` と `policy` は `tasks` と一緒のときだけ有効です。

三つの形は互いに排他で、ちょうど一つだけ渡します。各段には `subagent_type`、`tools`、`model`、`max_turns` も付けられます。`max_turns` は 4 から 32 へ挟まれます。

走り終わったら消えるのではなく、このセッションに残して、途中で新しい指示を送りたいサブエージェントもあります。同時に残せるのは最大 4 つで、操作できるのは自分が直接作ったものだけです。モデルがそれらを扱うツールは次です。

- `SpawnAgent`：`label` と `prompt` が必須です。`subagent_type` と `tools` は任意です。`tools` を空配列にすると、話すだけでツールは呼びません。
- `AgentFollowup`：`agent_id` と `message` が必須です。`mode` を書かないと `followup` で、今のターンの末尾に届きます。`steer` は今のツールの束が終わってから向きを変えます。
- `AgentControl`：`action` は `status`、`list`、`stop`、`release` です。`stop` と `release` には `agent_id` が必要です。`list`、または id の無い `status` は、このセッションに属するサブエージェントを見ます。

`release` は枠を返します。相手が止まっていて、資源の片付けが終わり、未送信の報告が無く、その相手がさらに持つサブエージェントも無いときだけ成功します。まだ動いている、まだ片付けている、または子を持っているときは `agent_busy` です。連続失敗で止まっていて、使用中の資源が無いときは解放できます。解放すると、それに対応するサブボリュームは消えます。

これらの管理ツールは、サブエージェント自身には渡しません。

サブエージェントは、指定しない限りメモリの中だけです。プロセス再起動のあと元どおり戻すなら、`subvolumeStore` と `rootDir` を渡します。ファイルは `<rootDir>/subvolumes/<parentSessionId>/<agentId>.json` で、パスはその親セッションのディレクトリから出られません。連続クラッシュは既定で 5 回（`restartLimit`。正の整数）で鎖され、再起動しても自分では解けず、あなたが `release` するまで鎖されたままです。ディスクへ書かないセッションサービスにはこの保管が無いので、サブボリュームもディスクへ書きません。

## 何度も呼ぶツールを、短いスクリプトの中に収める

何十もの途中結果を、このセッションの履歴へ積まないでください。`createCodemodeTool` を組み立てたあと、モデルは `Codemode`（名前は変えられます）で非同期のスクリプトを書けます。スクリプトは隔離された一度きりの worker の中でツールを呼び、このセッションが受け取るのは最終の戻り値と、長さの限られたログだけです。組み立てなければ、このツールはありません。

モデルは `code` と、任意の `timeout_ms` を渡します。既定は 15 秒で、指定した値の上限は 60 秒です。このセッションへ戻るテキストは既定で最大 32 KiB です。worker の旧世代ヒープは既定 48 MiB で、超えても止まるのはこの worker だけです。

スクリプト内の `await tools.<name>(args)` と `await callTool(name, args)` は、どちらも既存のディスパッチへ戻ります。権限の確認はそのまま必要です。一つのスクリプトでの入れ子呼び出しは、既定で最大 32 回です。スクリプトは `Codemode` 自身を再び呼べず、`Task`、`SpawnAgent`、`AgentFollowup`、`AskUser` も呼べません。

スクリプト内の `store(key, value)` / `load(key)` の既定は純メモリの表です。鍵は最大 64、合計 1 MiB、鍵名は最大 256 文字で、ディスクへは書きません。ディスクへ書かないセッションサービスも、この表を残しません。

ツールに `outputSchema` を宣言すると、成功結果はプログラムが読む `structuredData` を持てます。この余分なデータは、モデルへ送るメッセージには入りません。検証に失敗すると取り除かれ、構造化エラーになります。あとのフックがテキストを変え、同じ段で `structuredData` を変えないときも、余分なデータは取り除かれます。文章は伏せたのに、構造化フィールドに原文が残ることを避けるためです。

## ファイルを書いたあと、同じターンで検査を走らせる

`afterRun` は `createSession` の引数ではありません。クエリ環の選択肢に置きます。書かなければまったく走らず、ファイルを読むだけ、または普通の質問でも始まりません。

このターンで、あなたが名前を挙げた書き込みツールが成功して書き終えたときだけ、クエリが終わる前、セッションがまだ占有されているあいだに `verify` が呼ばれます。既定で見る名前は `Edit` と `Write` で、`mutatingToolNames` で変えられます。エラーの結果と、取消のために補われたプレースホルダは、成功した書き込みには数えません。

`verify` は、今回変わったパス、どのツールがやったか、何回目の検査か（1 から数える）、その時点のメッセージ、取消シグナルを見られます。`{ action: 'pass' }` を返せば終わります。`{ action: 'followup', prompt }` を返すと、同じクエリの中であなたの指示に沿って直します。`maxAttempts` の既定は最大 2 回です。それより大きい数は 5 へ挟まれ、`0` は記録するだけで直しません。ターン数、予算、取消シグナルも有効です。
