ここにある挙動は `tansr-cli` のメインラインに既に入っていますが、**公開済みリリースの CHANGELOG にはまだ載っていません**。npm の `@tansr/sdk` 0.20.1 と CLI 0.11.0 にはありません。これらの変更を含むパッケージへ上げるまでは、この節の呼び出しを書かないでください。

## セッションのハンドオフ

`createSession` で作ったセッションは、`handoffSession(session, options)` で新しい目標へ渡せます。元のセッションは読み取るだけです（直近のコンパクション要約、残した末尾の履歴、対になったファイル一覧）。新しい目標向けのブリーフを作り、種メッセージを 1 件だけ持つ新しいセッションを作ります。新しいセッションは `parentSessionId` を記録します。元のセッションは書き換えられず、あとから再開できます。

```ts
import { handoffSession } from '@tansr/sdk';

const next = await handoffSession(session, {
  goal: 'ship the retry change',
  reviewDraft: (draft) => ({ action: 'confirm', briefing: draft.briefing }),
});
if (next.status === 'created') {
  console.log(next.sessionId, next.parentSessionId);
}
```

- `goal` は必須で、空白だけにはできません。`reviewDraft` はブリーフ本文を差し替えられます。`{ action: 'cancel' }` を返せば中止です。中止、拒否、失敗のいずれでも新しいセッションは残りません。
- 同じファクトリで作ったセッションには、列挙されない `session.handoff(options)` も付きます。意味は `handoffSession` と同じです。型の上ではエクスポートされた関数を呼んでください。
- 同じエクスポートには `HANDOFF_PROVENANCE_TAG`（シードメッセージ上の引き渡し印 `tansr-handoff-v1`）、`buildHandoffSeedMessage`、`readHandoffProvenance` もあります。生成された SDK の記号ページは公開済みの 0.20.1 のままで、これらの名前はまだ載っていません。
- CLI の対話画面には `/handoff <goal>` が増えています。目標が空なら使い方を示すだけで、モデルは呼ばず、今のセッションも変えません。確認すると画面は新しいセッションへ移ります。元のセッションはディスクに残り、`/resume` で開けます。

## コミット済みノードからの分岐

スナップショットからの `fork` に加えて、メインラインではコミット済みの任意のノードから枝を分けられます。要約が覆うのは、元の枝から外れた差分とファイル一覧だけです。分岐点より前のコールドな区間は、まとめて読みません。

## コンパクション

ターンの途中でコンパクションが走ると、要約は二つに分かれます。終わった履歴と、まだ終わっていない現在ターンの接頭部分（元の依頼、実行済みの動作、これからつなぐ現場）です。ツール呼び出しとその結果は、要約の境界で分かれません。次のコンパクションは前の包みを先にほどくので、同じ接頭部分が何重にもなりません。

バックグラウンドの事前コンパクションは既定ではありません。`backgroundCompactMargin` を置いたときだけ、より早い水位に達しても本リクエストはすぐ送られ、バックグラウンドが読み取り専用のスナップショットを要約します。次のバリアで世代と材料がまだ合うかを見ます。セッションが消された、巻き戻された、または同期コンパクションがそのスナップショットを超えたなら、その要約は捨てます。`closeAsync()` は決着を待ち、使用量を記録します。

一回きりの補助リクエスト（コンパクション、枝の要約、一度きりの題名や分類）は、キャッシュの印を書かなくなりました。本セッションのリクエストと、常駐サブエージェントの本ターンは、これまでのキャッシュ方針のままです。

最初のターンのツール定義は、キャッシュの接頭部分として固定されます。あとから有効にしたツールは、その後ろへ足すだけなので、接頭部分全体を無効にしなくて済みます。

## 遅延ツールの発見

遅延候補のツールが 16 に達したとき、または明示的に強制したとき、`ToolSearch` が登録されます。その説明文は固定です。途中で MCP を繋いでも外しても、この文は変わりません。モデルは検索してからツールを有効にします。サブエージェントは各自の目録を持ち、ほかのサブエージェントが有効にしたツールは見えません。実際の実行は、これまでどおり権限の門を通ります。

## Task と常駐サブエージェント

常駐サブエージェントは同時に最大 4 つです。枠を返せるのは、そのサブエージェントが止まって後始末が終わったあとだけです。親セッションが操作できるのは、自分が直接作ったサブエージェントだけです。進行中のターンは、今のツール群のあとで `steer` により向きを変えるか、`followup` を並べられます。モデル向けの操作は `status`、`list`、`stop`、`release` です。

`Task` は単一のタスクをこれまでどおり受けます。ほかの形は互いに排他です。

- `chain`：1 から 6 ステップ。次のステップは `{previous}` で前の出力を受け取ります。途中の本文は親セッションの履歴へ書きません。
- `tasks`：1 から 8 件を並列に。`concurrency` の既定は 4、上限は 8 です。`policy` は `allSettled` または `failFast` です。`failFast` か親の中止では、終わっていない兄弟を止め、資源の後始末が終わるまで待ちます。

常駐サブエージェントは、明示したディレクトリへサブボリュームを書けます。プロセス再起動のあと、そのサブボリュームから温かい再開ができます。連続したクラッシュは既定で 5 回に達するとロックされ、再起動をまたいでもロックのままです。その枠を `release` するまで戻りません。ディスクを持たないセッションサービスは、このサブボリュームをディスクへ書きません。

## Codemode と構造化結果

ツールは任意の `outputSchema` を宣言できます。成功した結果は `structuredData` を持てます。このデータは、モデルへ送るメッセージには入りません。あとのフックが本文を変え、`structuredData` をそれに合わせなかった場合、構造化データは外されます。

`Codemode` は既定のツールではありません。アセンブリしたあとでのみ現れます。スクリプトは専用のワーカーで動き、時間とメモリに硬い上限があります。スクリプト内の `tools.<name>()` も、ホストの権限の門を通ります。スクリプト自身の状態はディスクへ書きません。

## 書き込み後の検証

`afterRun` は `createSession` のフィールドではありません。カーネルのクエリ環のオプションにだけあります。設定しなければ一切走りません。このターンで、設定されたファイル書き込みツール（既定は `Edit` と `Write`）が成功したあとに限り、クエリが終わる前、セッションがまだ忙しいあいだに `verify` が呼ばれます。`{ action: 'pass' }` で終わります。`{ action: 'followup', prompt }` は同じクエリの中で直し、既定では最大 2 回、硬い上限は 5 回で、ターン数、予算、中止信号にも縛られます。読み取りだけ、質問だけ、では起きません。
